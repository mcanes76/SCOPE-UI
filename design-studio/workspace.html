SCOPE operator workspace

The Workspace Manager runs in Studio previews, Final Presentation, standalone operator exports and configurable folder exports. Navigation architecture and visual family remain independent of workspace arrangement. The simulated applications and their data contracts are retained.

Arrange applications

Choose Single Application, Two Applications (side-by-side), or Stacked. Select applications independently. The same application can occupy both panes, sharing simulated data within that document with independent view settings. Focus identifies the active pane; Expand shows that pane alone, and Restore Split restores the arrangement and saved divider ratio. Swap moves the two application views between panes.

Drag the visible separator. Use Left/Right arrows for side-by-side, Up/Down for stacked; each press changes five percentage points, or one with Shift. Home/End move to the effective minimum/maximum. Double-click the handle or select Reset to 50/50. Focus and expansion preserve the ratio.

Minimum pane width/height constrain resizing. A narrow side-by-side workspace adapts to stacked rendering when two minimum widths cannot fit, while retaining its selected layout and ratio for a wider window. Ratios can be constrained to 50/50 temporarily; enlarging restores the configured preference. A tall minimum height can require scrolling. Browser zoom, target display dimensions and the application's own content can affect practical usability.

Detach and return

Each split-pane header has Pop Out; Single has an application-specific Pop Out in the toolbar. One tracked window per application per workspace is supported; requesting it again focuses that window. The main manager lists detached applications. The original pane remains available as a local view, so blocked or disconnected windows cannot remove access to an application.

Detached windows retain SCOPE branding, configured application labels, logo, visual family, selected typography and component overrides. They contain one operator toolbar with Return to Workspace and Close Window. Return sends a validated request to its originating workspace, restores the application to its original pane when possible (or the primary single view), attempts to focus the main window and closes the child. It replaces a pane assignment rather than adding a pane. A main-workspace Return action can close tracked windows using the original local view when a child cannot communicate.

If the originating workspace is missing, the child remains usable and offers Save Updated Mockup and Close Window. If a live opener does not acknowledge a return, a timeout message explains those alternatives. A saved detached mockup reopens as a normal standalone single-application workspace; it does not preserve a stale opener identity. The browser may require closing a tab manually.

State ownership

StateBehavior
Shared presentationBranding, labels, logo, theme and component overrides are copied on launch and updated from the originating window through authenticated messages. A workspace ID identifies related windows.
View-local settingsTabs, selections, camera zoom/orientation and model-backed drafts are copied on layout transitions, swap, launch and return when preservation is enabled. Missing BLOS group IDs map to an available local group. Calibration drafts keep revision checks; an independent draft can be stale and rejected by the existing simulation.
Simulated dataShared within one document, independent between windows. Return does not merge multicast membership, sensor values, LOS updates or other simulated data. No operational backend synchronization is provided.
Transient DOM stateReplacing a pane or changing navigation can rebuild host DOM. Unsaved DOM-only edits, selection/caret, focus, scroll position and open dialogs are not guaranteed across that rebuild. Model-backed form drafts and per-view maps remain. Palette-only changes and side-by-side/stacked conversion avoid replacing application DOM.
Session lifecycleClosing and reopening starts the embedded/configured initial layout and fresh simulated stores. Live window handles and session IDs are not persisted. Use Design JSON or Save Updated Mockup for deliberate configuration persistence.

“Preserve compatible view settings” controls copying during layout changes, swapping, launch and return. Existing view maps are still maintained by the applications. It does not imply cross-window data synchronization or guaranteed DOM state preservation.

Messages and deployment

The implementation uses direct window messaging because a known opener and child handle provide a narrow identity boundary. BroadcastChannel was considered but is unnecessary for this lifecycle and cannot reliably bridge opaque file origins. Return/ready/closed messages require protocol version, workspace ID, window ID, application index, per-window token, exact source window and matching origin. View payloads accept bounded JSON only, reject prototype keys and non-finite values, and validate application field types. No payload HTML or code is evaluated.

HTTP windows must share an eligible origin. Standalone file and Blob windows can report an opaque null origin; outbound messages then use a wildcard target while receivers still verify exact source, token and identity. Browser isolation, popup restrictions and focus/close policies vary. If return messaging is unavailable, keep working in the local pane, use its Return button to close tracked children, or save and close the child manually. Automatic neighboring-file fetch is never required for standalone operation.

Studio and configuration

Guided Workshop → Layout offers the three arrangements and Allow Pop Out. Advanced Editor → Global typography & layout includes assignments, ratio, minimum sizes, allowed layouts, permission and preservation policy. Workspace headers/frames and controls use the existing component cascade; individual controls have semantic IDs such as shell.window.button.divider, shell.window.button.swap and shell.window.button.popout.left. Pane headers inherit Headers; the divider also inherits Frames, and workspace selectors inherit Buttons. Application Join/Leave/Warning/Create colors remain application-owned.

workspace.schema.json documents the optional version 1 workspace object in design JSON and params.json. This is an additive extension to design schema 1 / parameter schema 2. Old layout.mode and operator defaults remain accepted; old explicit allowed modes retain their restrictions. For new files, use the canonical workspace object:

{
  "schemaVersion": 2,
  "initial": {"theme": "slate-light", "navigation": "deck"},
  "workspace": {
    "schemaVersion": 1,
    "layout": "stacked",
    "left": "blos",
    "right": "display",
    "ratio": 60,
    "minPaneWidth": 240,
    "minPaneHeight": 180,
    "allowedLayouts": ["single", "split", "stacked"],
    "popout": true,
    "preserveViews": true
  },
  "branding": {"name": "SCOPE"},
  "logoPath": "assets/logo.png",
  "applications": {"blos": {"name": "Link Manager"}}
}

Workspace fields take precedence over legacy initial layout/apps and allowed modes. Ratio bounds are 10–90%; minimum width 160–640px and height 120–480px. The selected layout must be allowed. Runtime focused/expanded pane and previous layout can be included in design snapshots; live window records are session-local. Legacy ratio input through the operator API retains its previous out-of-range clamping behavior.

Folder exports include params.json and a replaceable logo asset. Serve the extracted folder over local HTTP for automatic loading. Standalone HTML embeds its defaults and supports Configuration → Import Parameters JSON / Import Logo Image and Save Parameters JSON / Save Updated Mockup. JSON, CSS, checkpoints and Final Presentation use the same workspace model and theme compiler.

The workspace validator builds a temporary candidate before distribution. Controlled fixtures run the requested sequence for Slate Light, Graphite Dark, DISCO, Field Ops — Night and Electric Glass across all four navigation architectures: single → split → 60/40 → focus → expand/restore → swap → stacked → detach/return → theme change → reopen. Additional checks exercise both keyboard and pointer axes, responsive constraints, invalid messages, blocked popups, one toolbar, JSON/checkpoints, Studio settings and ZIP assembly.

Browser acceptance remains pending. This session exposed no browser surface. Fixture results do not verify native popup placement, file-origin behavior, actual CSS layout, operating-system focus, dropdown rendering, touch/pointer capture or screenshots. Repeat the sequence in current Edge/Chrome from the exported standalone file, using the same application arrangement under all five palettes; check keyboard focus, native window closing, narrow viewport adaptation and offline reopening before customer acceptance.
