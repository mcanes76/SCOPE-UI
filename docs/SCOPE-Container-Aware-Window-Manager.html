Phase B: Container-Aware Window Manager Sizing

Implemented on feature/scope-app-integration, starting from clean checkpoint 5b6aa8d. Scope is Window Manager measurement and geometry only. The reverted compact toolbar and Display redesign remain removed. Context Panel visibility, content, placement, configuration and Studio preview controls are unchanged. No Phase C or D work is included.

Host measurement

The managed stage no longer uses 100dvh - 260px. In a browser, its actual top edge and width are measured with DOM geometry. The sizing pass walks shell-owned ancestors, accounting for normal-flow siblings below the stage, their margins, parent padding/borders, visible scrollport/declared height constraints and the actual viewport boundary. Chrome above the stage, including wrapped toolbars, is already reflected in its measured top. A Context Panel below the host is included as trailing shell space; a side rail is not incorrectly subtracted from height. No application-owned DOM is traversed or resized internally.

The positioned Aperture dock normally fits in the existing host padding. If its measured height and bottom offset require more room, additional padding is reserved below the managed task row, preserving the existing dock and toolbar presentation. Existing document scroll is accounted for so it cannot inflate the budget. The resulting stage client dimensions, excluding its border, are passed to the geometry model.

While managed mode is active, default minimum-height floors on the shell and relevant layout containers are temporarily relaxed; any explicit shell-region minimum is honored. Prior inline minimum styles are restored when leaving managed mode. There is no global body flex conversion, page overflow lock, Context Panel collapse or preview CSS change. Application content continues scrolling inside the existing managed body.

A soft 180px stage minimum keeps window controls usable when shell chrome alone exhausts a short viewport. A genuinely smaller bounded host takes precedence. Necessary page scrolling can therefore remain in small previews or when the unchanged Context Panel occupies substantial space. Completely hidden, zero-width or collapsed bounded hosts defer initialization/fitting rather than generating 1px window geometry. Open requests can wait for reactivation. A 300px initial CSS fallback is used only before measurable browser layout is available.

ResizeObserver watches the stage and shell ancestors/siblings, not application internals. Notifications are coalesced through requestAnimationFrame, height writes occur only when the result changes, and fitting/painting occurs only when bounds change. Browser/visual-viewport resize and normal shell render/configure paths also measure. Observer subscriptions are replaced only when the shell path changes. CSS visibility-only changes without a resize must use the normal shell decoration/reactivation path. Read-only ScopeManagedWindows.measure() exposes the last sizing budget for diagnostics, without an operator-facing panel.

Initial sizing and restore semantics

A new first managed window opens in normal state, centered with a nominal 16px gutter where space permits. It starts from the application's existing preferred dimensions and uses 75% of any additional available width/height. When space is smaller than the preference, only its displayed rectangle is constrained; its intended size retains the application preference for later enlargement. Existing saved initialized layouts are never reinitialized to this policy. Later window launches and explicit cascade/reset arrangements remain bounded, with the existing application size profiles. Browser Pop Out requests continue using the unchanged legacy non-fullscreen initial-size path.

restore now represents intended normal geometry; rect is the current constrained display rectangle. Fit operations derive the latter without shrinking the former. Enlarging a workspace therefore recovers the prior dimensions/position where possible. A deliberate move updates intended position while retaining a temporarily constrained size. A deliberate resize establishes a new intended rectangle. Maximize, docking, minimize/reopen and close/reopen preserve normal intent; explicit Restore returns to that intent under current bounds. These operations never alter application state.

Tile adds optional tile:{column,row,columns,rows} placement metadata to each tiled window, allowing cells to remain proportional and non-overlapping while the grid fits. If shrinking would make cells smaller than usable window minima, rendered windows temporarily cascade without discarding their tile intent; enlargement restores the grid. Maximize/dock/restore can retain the tile placement; a manual move/resize or Cascade leaves it. Existing JSON without this optional field remains valid, and design schema version remains 1. Current Studio and newly generated standalone runtimes accept and export it. Older exported HTML must be regenerated to understand the new optional placement metadata and sizing logic.

The focused validator exercises intended geometry through shrink/enlargement, creation in a small host, deliberate movement/resizing, tiled placement, maximize/restore, dock/undock, minimize/reopen and close/reopen. For supplied 1920×1080, 1600×900 and 1366×768 viewport fixtures, the calculated stage outer heights are 721, 541 and 409px respectively. These values use fixture chrome and are not actual browser measurements. No before/after screenshot, native scroll-height pass or visual acceptance claim is made. The browser access host was unavailable during this task. Actual Chrome/Edge rendering, iframe scaling, glyphs, pointer/wheel interactions and responsive clipping remain manual acceptance work.

Known limits: existing configurations whose restore geometry was already lost cannot reconstruct it; extremely small bounded hosts can still require maximize/manual rearrangement to expose content; existing Context Panel and shell chrome may still require page scrolling; and previously exported files retain their old runtime until regenerated. Native CSS transforms or unusual custom positioning outside the supported shell structure require browser review. This implementation does not expand previously saved windows merely to fill empty space. Phase C/D defaults and preview changes remain out of scope.
