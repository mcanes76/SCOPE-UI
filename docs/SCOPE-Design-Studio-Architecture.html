Purpose and intended audience

SCOPE Design Studio is a customer-facing design exploration tool built around the SCOPE Integrated Electric Glass mockup. It supports collaborative selection of navigation, material themes, typography, colors and shell-level arrangement, with an immediately updated preview. It is a presentation and decision-support demonstrator—not a production operator application or a mechanism for changing domain behavior.

Operating modes

Three modes share a design configuration: Guided Presentation, Advanced Visual Editor and Final Presentation. Guided Mode structures a roughly 15-minute workshop; Advanced Editor offers finer-grained shell appearance and layout controls; Final Presentation hides editor chrome and reveals simulated application details for review.

Design principles

One source of design truth; progressive disclosure during customer review; strict separation of SCOPE shell versus application ownership; instant visual feedback; explicit recovery through Undo/Redo and saved candidates; reproducible outputs; and no implication of live operational connectivity.

Workshop sequence

The customer first chooses a navigation model while detailed sub-UI content is hidden, then evaluates themes, colors/borders, typography/density and constrained layout. The last step reveals the simulated application interfaces in the finished shell. The steps are facilitation guidance, not verified timing measurements.

Outcomes and limitations

Intended outcomes include one or more design candidates, an agreed preferred presentation, a configuration artifact, and a record of customer rationale. Visual preference alone does not validate usability, accessibility, interface integration or operational suitability. Actual testing is required on the intended display and in the intended lighting environment.

Scope disclaimer. The source reference documents SCOPE UI architecture and concept validation; it does not establish the Design Studio implementation internals. The Studio architecture here is based on the agreed feature design and Codex completion report, with observed behavior distinguished from unverified behavior.

System context

One source implementation serves two distributions: design-studio/index.html for HTTP development, and generated dist/SCOPE-Design-Studio.html for customer double-click launch. The offline artifact embeds the same editor, engine, CSS, configuration, logos, Earth texture and help. Its runtime needs only a browser; Node.js is developer-only packaging tooling. Neither distribution connects to operational services.

Logical components

studio.js owns the workshop/editor UI; design-core.js owns validation, design state, history, candidates, effective preset tokens and CSS compilation; exports.js owns artifact composition. preview-runtime.js applies bounded shell commands to the existing Electric Glass engine, with preview-bridge.js authenticating messages. The optional offline.js supplies embedded resources and sandboxed srcdoc frames. embedded-windows.js packages independent application pop-ups from the current embedded engine document. scripts/build-standalone.cjs generates the customer file from these sources; no duplicate application renderer is maintained.

Ownership boundary

The Studio may alter shell colors, typography, material treatment, navigation mode, shell region sizes and visibility. The BLOS, Display, Sensor Calibration and Native LOS sub-UIs retain ownership of their internal widgets, validation, data models and simulated workflows. A locked sub-UI container may inherit approved shell theme tokens; its inner structure is not offered for visual editing.

State ownership and lifecycle

A single logical design state is shared by Guided and Advanced Mode, with distinct transient editor state (selected shell region, open inspector, active step) and separate simulated application state. Pure appearance changes should not reinitialize the preview. Navigation changes should preserve current application selection where possible. Saving a candidate captures design settings; it does not imply operational data persistence.

Preview bridge contract

Messages use namespace scope-design-studio, version 1 and a random per-frame channel. Both sides check the source window, origin, channel, version and accepted message types. The preview accepts validated configure messages; it reports ready, applied, selection, application, resize and error. Appearance edits replace shell CSS without unmounting application content. Navigation changes reuse the engine render path, retaining model stores and per-slot view state.

HTTP development loads the engine by URL and requires an exact same-origin match. Offline previews use iframe.srcdoc with an opaque sandbox origin; the sandbox grants scripts, modal dialogs, downloads and user-initiated pop-ups, but does not grant same-origin access. A wildcard targetOrigin is required only when addressing an opaque-origin destination; source-window, expected-origin and channel checks still apply. No global relaxation of origin checks or browser security settings is used.

Architectural tradeoffs

An isolated iframe reduces style collisions but adds communication and focus/resize complexity. Direct in-document rendering can simplify editing but risks CSS and event coupling. Token-driven changes improve consistency but restrict arbitrary styling; local overrides improve precision while increasing complexity. Constrained shell resizing is preferred over unrestricted drag/drop because each navigation concept has different structural rules.

Section 03 / Interaction Model

Workshop, editor & final reveal

Guided Mode

Six stages: (1) Navigation—Aperture, Mosaic, Portal or Command Deck; (2) Theme—available material presets, including Electric Glass variants; (3) Colors and borders; (4) Typography and density; (5) Shell layout; (6) Final review with simulated detail reveal. Only the relevant subset of controls should appear at each step. Back/Next and revisiting completed stages must preserve choices.

Advanced Editor

A three-region workspace presents the shell structure tree on the left, the real preview in the center and the selected region's property inspector on the right. Selecting a header, navigation region, workspace container, context rail or footer identifies allowable properties and highlights the region. Application-owned inner controls remain read-only.

Property scope

Global design tokens influence all eligible shell regions. Selected-region overrides apply only to approved containers and can be cleared to inherit the theme default. Typical editable properties are background, border color/width/radius, typography, opacity, padding, spacing, width and visibility. Semantic success/warning/error colors must remain distinct from decorative accents.

Header/BrandingSurface, height, logo presentation, visibilityPreserve orientation and logo aspect ratio

Shell resizing

Navigation and context widths can be adjusted only where the current navigation mode supports those regions. Set minimum/maximum widths and preserve a viable workspace. Avoid arbitrary rearrangement of BLOS and other application controls. Validate at multiple browser sizes and zoom levels.

Candidates and comparison

Baseline and Candidate A/B/C store design snapshots in memory. Select a checkpoint and Restore to load it into the shared state. Compare checkpoints opens two side-by-side previews of saved designs, with details hidden and fresh independent simulations. In the offline edition both previews come from embedded srcdoc resources. Candidate names, workshop notes and design-only Undo/Redo behavior remain unchanged. Export each candidate as JSON before reloading; checkpoints are not durable project storage.

Final Presentation Mode

Final Presentation removes the Studio editing controls, applies the selected design and shows simulated sub-UI details. Reviewers may navigate between applications while the shell settings remain. A Return to Studio control should restore editing without discarding the design. Native browser full screen may require explicit user interaction and can be blocked by policy.

Section 04 / Configuration & Artifacts

Schemas, export & portability

Configuration separation

mockups/params.json configures branding, logo paths, application names and tab/navigation labels. design-studio/theme-presets.json is the authoritative current palette/material source. design-studio/design-config.json is the actual startup design. Exported design JSON files are customer snapshots, loaded explicitly through Import; scope-design.json is not the startup file. Keep stable application IDs independent of display labels.

The current presets are Electric Glass, Prism Glass, Nocturne Ink, Carbon Cobalt, Spectrum Blocks, Frosted White, Electric Glass – White Trim, and Electric Steel, Teal, Violet, Olive, Amber, Indigo, Cyan, Green and Slate. All 30 presets and four navigation modes (Aperture, Mosaic, Portal, Command Deck) are bundled without replacing their engine materials. Frosted White retains the existing cool white translucent Prism treatment.

This is the version 1 startup schema used by the source and bundle. Imports validate known fields, fonts, hex colors and region targets, clamp finite dimensions, and reject unsupported versions or application-owned properties.

Token strategy

Expose a small documented semantic token layer for surface, text, border, accent, typography, spacing and glass treatments. Apply global tokens first and then approved shell-region overrides. Prevent accidental remapping of status semantics into decorative accents. CSS export should record the selected values and any required selectors for reproducibility.

Import and export contracts

Both editions provide design JSON download/import, CSS overrides, a standalone final mockup HTML and a printable HTML decision summary. The offline export path composes from embedded engine resources rather than fetching sibling files. All Electric Glass scheme defaults and explicit overrides are reflected in the generated CSS. Standalone final mockups include code, CSS, labels, design, logos and Earth imagery; details are visible and simulation data starts fresh. The final mockup export is distinct from the complete Studio distribution.

Imports use the browser file picker and local File APIs; downloads use Blob URLs. No server is needed for these operations in the offline edition. Native download prompts and pop-up placement remain browser-controlled. Exported designs and decision notes are customer review artifacts, not operational configurations.

Logo and label configuration

Branding should use the configured logo path, fall back to the default SCOPE crosshair asset, preserve image aspect ratio and not require code changes to rename application labels. The existing mockup configuration work introduced params.json and logo support; confirm the actual paths and configuration keys in the repository before treating them as a guaranteed interface.

Offline distribution boundary

The customer artifact is dist/SCOPE-Design-Studio.html. Copy or extract this one file and double-click it in current Edge or Chrome. No sibling assets, launcher, local server, installation, internet, extension or browser security change is required by its code. Development files stay modular and still use HTTP.

Packaging embeds configuration and raw engine resources as escaped JSON, inlines the editor stylesheet/scripts and default logo, and removes runtime JSON loading from embedded engine documents. The same export composer builds live srcdoc previews and final exports. User-initiated independent windows use embedded HTML Blob URLs and retain their separate simulation sessions. Help and its mockup link also resolve to bundled documents. There are zero required automatic external or localhost resources in the packaging audit.

Section 05 / Deployment & Security

Local, customer & presentation

Development and local review

For source development, run python -m http.server 8080 --bind 127.0.0.1 from the repository root and browse to http://127.0.0.1:8080/design-studio/. Keep shared relative paths intact. For offline customer review, open dist/SCOPE-Design-Studio.html directly instead; the customer does not run this command.

Developers regenerate with node scripts/build-standalone.cjs. The build reads the current source/configuration/assets, validates presets and startup design, and writes a deterministic UTF-8 HTML file. Rebuild after source, branding, logo, preset or initial-design edits. Generated output is separate from source and must not be hand-edited.

PowerPoint handoff

Use a concise PowerPoint launch slide with a hyperlink to the already-running local Studio or an approved hosted URL. PowerPoint controls the presentation narrative; the browser handles interactive design. A hyperlink to 127.0.0.1 works only on the computer running the corresponding local server. A static screenshot or short recording should be available if the live demonstration fails.

Customer distribution choices

Distribute only dist/SCOPE-Design-Studio.html for the complete offline Studio. It can be copied to another folder or computer or placed in a ZIP; after extraction the HTML is the only required file. Internal HTTP hosting and the modular development edition remain alternatives. A browser Blob URL is temporary and must not be distributed as a saved file link; distribute the actual downloaded HTML.

Candidate checkpoints remain session-only. Download customer JSON/summary/final HTML before closing. Normal browser controls govern fullscreen, file selection, download prompts, multiple pop-ups and window placement; no feature is silently removed to bypass these controls.

Trust and data handling

Treat design configurations and imported files as untrusted input. Validate values, file types, length, allowed paths and CSS override targets; do not evaluate imported JavaScript or arbitrary CSS text. Do not expose internal-only customer details or publish engineering mockups on public hosting without approval. Avoid collecting sensitive operational data in workshop notes.

Operational separation

Studio-generated configurations are design-review artifacts, not approved production configurations. The existence of an application tile or a simulated status does not establish backend integration, authorization or readiness. No real REST operations, customer networks or live system controls should be assumed from the Studio mockup.

Section 06 / Validation & Decisions

Evidence, acceptance & open items

Reported implementation evidence

Source and packaging validators have been run against the implementation. Packaging checks cover deterministic generation, inline script compilation, embedded assets, zero automatic external resources, all 120 shell/preset combinations, opaque-origin message authentication, protected application boundaries and shell state retention. Actual editor handlers exercise six guided steps, Advanced/Final transitions, design history/candidates/comparison, JSON import and all exports with fetch configured to throw in offline fixtures. These are controlled JavaScript fixtures, not proof of browser rendering.

Observed user verification

Earlier user observations established development startup through a local server and candidate Save/Restore. The packaged offline implementation has now been inspected and exercised in automated fixtures, including side-by-side candidate comparison and standalone export composition. No browser automation surface was available for this packaging task. Actual Edge/Chrome file:// launch, visual fidelity, native pointer dragging, download behavior, fullscreen, pop-ups and printing remain unverified by browser testing.

Acceptance test plan

Verify six guided steps and real-time preview; all four navigation modes; theme, typography and border changes; selectable/locked shell boundaries; constrained resizing; Undo/Redo; candidates and restore; JSON round trip; CSS generation; portable HTML export; final reveal; return without losing selections; branding fallbacks; keyboard navigation; and browser responsiveness. Record pass/fail per test rather than inferring results from validator success.

Browser and accessibility review

Codex stated native Chrome/Edge interaction testing was unverified due to unavailable browser surfaces. Perform actual keyboard/pointer tests, focus checks, zoom/narrow-window tests, print/export inspection and representative customer walkthroughs. A 15-minute target is a design assumption until measured in a rehearsal.

Open architectural questions

Remaining acceptance work is native Edge/Chrome file:// review on the customer environment, target-display ergonomics, full keyboard/focus review, PDF pagination and a timed workshop rehearsal. Durable project storage, candidate bundles and real application embedding contracts remain future work. Application integration, authorization and operational readiness cannot be inferred from this design tool.

Release and change-control recommendation

Maintain the Design Studio in the same Git repository as SCOPE UI, preferably on a feature branch until accepted. Preserve the original mockup as a baseline, store generated configs separately from source defaults, validate changed artifacts, and version exported configuration schemas. Use this document as architecture reference, not as proof of acceptance.
