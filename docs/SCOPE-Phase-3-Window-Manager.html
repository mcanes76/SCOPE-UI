Phase 3: Operator Workspace Window Manager

Phase 3 introduced managed windows into the SCOPE prototype at 30bf8d6. This guide includes the subsequent container-aware sizing, Context Panel and Studio preview sizing changes. Phase 1 Component Editor and all 31 legacy presets remain. Phase 2 Visual Families, Compact Workspace and Display Map-Centric Layout were reverted.

Open dist/SCOPE-Design-Studio.html directly in Chrome or Edge. The default operator workspace uses managed application windows. Use Open BLOS, Open Display, Open Sensor Calibration or Open Native LOS above the window area. Reopening an already open application focuses its existing window; a minimized application is restored. The shell navigation and its existing application switcher also open managed views. Aperture, Mosaic, Portal and Command Deck are navigation concepts. Single Application, Two Applications, Stacked and Managed Windows are application arrangements. Each uses the shared, optional Context Panel in its workspace view. The legacy single, side-by-side and stacked toolbar buttons switch back to the existing layouts. Managed Windows returns to the managed area. Guided/Advanced → Layout offers the same mode switch.

Drag a title to move a window; drag its bottom-right Resize handle to resize. Title arrows move by 10px; Shift+arrows resize, as do arrows on the Resize handle. Escape or pointer cancellation cancels an active drag. Title-bar controls provide Minimize, Maximize, Restore, Dock left, Dock right, Close and permitted Pop out. The taskbar restores minimized windows. Clicking or tabbing into a window raises it and adds an active outline and textual Active marker. Maximize is an explicit action. Native pop-outs request modest, centered sizes rather than the entire screen; browser/OS policy can override placement.

Preferred dimensions in CSS pixels are BLOS 760 by 560, Display 820 by 560, Sensor Calibration 780 by 620 and Native LOS 640 by 480. The first window opens centered in normal state, with approximately 16px of gutter where space allows and 75% of the extra space beyond its preferred size allocated to it. Additional opens and explicit Cascade use the existing offset and approximately 82% width and 80% height caps. Reset workspace initializes one normal primary window and hides the other cached windows, retaining application data. Browser pop-outs use separate sizing.

The managed runtime measures the shell host, accounts for the visible viewport and trailing shell chrome, and passes stage client dimensions to the geometry model. ResizeObserver changes are coalesced into animation-frame measurements. Normal minimums are 420 by 300, reduced when the host is smaller. restore holds the intended normal rectangle. rect is its constrained rendering. Shrinking and enlarging the host preserves intent. A deliberate move changes intended position and a deliberate resize sets a new intended rectangle. Restore uses that intent under current host bounds. Docking uses halves when at least 840px is available and fills the host on narrower screens. Tile keeps optional cell placement metadata, temporarily rendering a cascade when cells would be too small. A later enlargement restores the grid. In Studio, zoom changes the outer display of the preview and leaves the measured logical host intact.

Each application has exactly one managed window and a stable managed-<application> engine view slot. The existing registry already supports per-slot views with shared engine stores. Window actions change shell geometry, visibility and stacking, without replacing application DOM. Close hides and caches the view so reopening retains uncommitted controls; application-owned data refreshes still use the existing application pipeline. The normal layout transition can reconstruct shell hosts; managed DOM is parked and returned intact. Compatible view objects seed managed slots on entry. App-owned forms, stores, modules, operations and #demo-action-dialog are not rewritten. Separate browser pop-outs retain the existing independent simulation lifecycle; returning imports compatible view settings only, not simulation stores.

Phase 1 panels/buttons/header styling applies to managed frames and controls through the existing classes and stable shell.window.button.* IDs. The restored global theme-role integration retains its existing behavior. The window manager is a small model/runtime adapter, with no framework or new runtime dependency.

Portable workspace schema 1 gains optional windowed (default true) and windows settings. windows stores initialization state, active application, ordered unique application rectangles, restore rectangles, normal/maximized/minimized/closed state and docking, with optional tile placement metadata. It contains no DOM, application stores or native window handles. Old workspace/parameter/design JSON remains valid. Use workspace.windowed: false to retain classic behavior explicitly. Existing design history, Candidates A/B/C, comparison and JSON/CSS/HTML/folder exports remain supported. Geometry is saved with design/parameters JSON, standalone operator exports and Save Updated Mockup; rectangles are fitted to the receiving workspace when reopened. CSS export retains the styling overrides; portable window geometry belongs to JSON/HTML. Checkpoints and history retain their existing session-only lifecycle.

Shell #switcher, #window-manager and Component Laboratory #confirmation dialogs use content-sized centered layouts, at most 680px wide and 85vh high, with scrolling and a translucent backdrop. Native modal focus trapping and Escape remain in control, with launch focus restored on close. Operator Configuration is a bounded scrollable popover; Escape dismisses it when no modal is open. The checkpoint comparison dialog is bounded to 1100px or the available width, with a height of 85dvh. Both previews share one logical resolution and visual scale. Application-owned dialog internals and sizing are excluded from these changes.

Implementation files:

  • design-studio/workspace.js, workspace.schema.json: validated, pure geometry model and backward-compatible workspace settings.
  • design-studio/workspace-windows-runtime.js: stable application hosts, pointer/keyboard interaction, focus/stacking, bounds, docking and shell popup constraints.
  • operator-runtime.js, preview-runtime.js, studio.js, studio.css: existing operator/history protocol, classic/managed mode transitions and Studio controls/dialog sizing.
  • exports.js, embedded-windows.js, scripts/build-standalone.cjs, and the engine's Studio loader: include the new runtime in source, standalone, saved and detached workflows.
  • docs/assets/validate-window-manager.cjs: model, real runtime handler and controlled DOM identity tests. Existing workspace tests explicitly select classic mode; source Studio checks cover the new runtime resource.

Validation covers all window actions, repeated opens without duplicate managed mounts, pointer/keyboard/cancel behavior, bounds from 300×200 through 1600×1000, preserved DOM identity/drafts/stores, theme/classic-layout transitions, resets, stable decoration, shell modal return focus, history/candidates/JSON/HTML/folder persistence and unchanged theme role maps. Run all existing validators as regression coverage, including Phase 1 and source/distribution parity. validate-window-manager.cjs also creates .validation/window-manager/operator-review.html, a self-contained three-window review artifact.

Phase 3 recorded controlled DOM evidence. Later Phase D headless Chrome and Edge tests exercise native pointer moves/resizes in the scaled frame and check managed bounds, state retention and standalone parity. Headed browser review still covers full keyboard/focus behavior, theme and title-bar rendering, native pop-out policies and target hardware. Geometry edits retain the DOM, but application operations may refresh their own forms through their existing code. Switching classic layout hosts can reset transient focus/scroll as before. Very small workspaces necessarily use the available dimensions and scroll application content. Exported simulations still start fresh. The manager has no cross-reload browser storage beyond explicit exports.
