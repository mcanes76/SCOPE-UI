SCOPE UI target architecture

Status: design exploration and architectural recommendation. No stackup internals, endpoint schemas, deployment platform or frontend framework have been supplied. This document describes the target shape, not a phased delivery plan.

A. Purpose and scope

SCOPE gives operators a common browser entry point for independently developed BLOS, Display, Sensor Calibration and Native LOS applications. The shell makes applications discoverable and provides consistent navigation, context and feedback. Each application retains its functionality, backend, owner and release lifecycle. BLOS already exists; this effort neither redesigns it nor assumes it can be embedded.

The single-file demonstrator explores presentation and local interactions. Its shared JavaScript and embedded CSS are packaging conveniences for offline review. Production need not share that runtime or form a monolith. The reserved src/ directory contains no production application.

E. Decoupling strategy

  • Independent development: each application publishes an integration contract and tested compatible versions. The shell consumes those contracts rather than private implementation details.
  • Backend ownership: applications call their own REST boundaries; any shared gateway enforces policy without merging domain implementations.
  • Module isolation: default to a separate browser document or separately hosted launch. Same-realm modules require explicit trust and lifecycle compatibility.
  • Shared contracts: define application identity, approved entry location, integration mode, navigation intents, lifecycle and failure reporting. These are shell integration concerns, not guessed REST fields.
  • API versioning: owners declare compatibility and deprecation policy. Adapters absorb supported variations; incompatible versions show a meaningful integration failure.
  • Application discovery: an approved registry drives application names, order, entry location, required permissions and declared capabilities. Validate configuration against a versioned schema. Do not discover arbitrary URLs supplied by operators.
  • Failure isolation: asynchronous independent initialization, per-application timeouts, bounded retries and cancellation. A failed app must not block application switching.
  • Change propagation: design tokens and shared components use explicit versions. New versions require compatibility review, not silent global replacement. A common visual standard can be implemented by different frameworks.
  • State ownership: keep shell selection and preferences separate from domain state. Cross-application communication uses narrow, versioned intents; do not build a shared global domain event bus.

For additions, an owner supplies an approved registry entry and demonstrates integration-contract compatibility. Existing applications should not need code changes. Whether registry changes require a shell deployment depends on configuration delivery policy, which remains open.

Micro-frontends describe organizational/composition boundaries, not a single isolation technology; frames and Web Components can both be used within that approach. Separate hosting does not itself provide same-realm isolation when code is imported into the shell.

Recommendation: use a framework-neutral shell and approved registry supporting launch integration first as a capability, and isolated embedding when verified with the owner. Offer shared tokens and standards. Adopt same-realm modules or Web Components only where benefits outweigh the additional trust and runtime coordination. No evidence yet justifies mandating React, Vue, Angular or another application framework.

For iframes, assess frame-ancestors on the embedded application and frame-src on the shell, sandbox capabilities, permissions policy, authentication redirects and storage behavior. Sandbox settings must be selected for the actual origin and required capabilities; do not copy a permissive template. The MDN iframe reference describes the relevant controls and sandbox limitations.

G. REST/API integration architecture

Application owners publish their API contracts and semantics, preferably in machine-readable form when available. SCOPE must not infer an API from rendered UI labels. No endpoint paths, payloads or sensor operations are specified here.

Configuration resolves approved environments and API locations independently of the visual concept. Browser-direct REST calls require the appropriate origin, credential and CORS policy. A gateway can simplify origin and session policy but adds an availability dependency and must remain narrowly scoped.

An adapter may normalize shell-relevant availability, generic error categories or timestamp formatting after actual contracts are supplied. Keep raw domain meaning, units and operation semantics with the owner. Do not equate a loaded UI with a healthy backend, or a successful network request with a completed domain operation.

Use bounded timeouts, cancellation on navigation, correlation identifiers and documented retry policies. Retry only operations whose contract makes retries safe; avoid duplicate mutations. Distinguish unauthenticated, unauthorized, unavailable, invalid input and incompatible integration. Preserve recoverable work and expose freshness where data is retained.

Authentication should follow the organization's chosen identity model. Shell and applications may share an identity provider without sharing raw tokens through browser messages. Backends independently enforce authorization on every protected operation. Cookie/session policies, CSRF protections for cookie-authenticated mutations, CORS and credential handling depend on deployment topology and must be agreed before integration. Session expiry must not silently resubmit a previously confirmed command.

H. Common UI design system

Publish semantic tokens for surfaces, text, boundaries, accent, success, warning, error and information; typography, spacing, radius and focus. Components consume the semantic layer rather than arbitrary concept colors. The prototype's twelve palettes are alternatives, not twelve production themes to support simultaneously.

The shared component contract includes accessible names, default/hover/focus/pressed/selected/unselected/disabled states, loading and outcome feedback where applicable. Unselected remains actionable. Disabled is unavailable. Pressed is transient; selected persists. Status is expressed with text and symbols as well as color. Passive statuses do not acquire artificial pressed states.

Navigation positions remain stable. Explain unavailable applications rather than removing them unexpectedly. Modal confirmation states the action and context, uses conservative initial focus and restores focus. Scope shortcuts so embedded applications retain their own keyboard behavior. No repeated flashing or unnecessary autonomous motion.

Native HTML behavior is preferred for forms and disclosures. For custom tabs, implement tablist/tab/tabpanel relationships, a single tab stop, arrow keys and optional Home/End as described by the WAI-ARIA tabs pattern. This prototype uses automatic activation on arrow navigation.

J. Failure and degraded operation

The shell renders independently of application startup. Distinguish unconfigured, initializing, available, unavailable, unauthorized, stale and incompatible states when supported by real evidence. The prototype only illustrates available/unavailable and local control feedback.

If one application fails, retain its navigation identity, explain the state and allow switching. Offer retry only when it has defined behavior. A launch integration cannot guarantee in-shell health visibility without an owner-provided signal. Frame load events alone do not prove readiness; use a versioned handshake if the application supports one. A missing handshake becomes unknown or unavailable after the agreed timeout.

Discard late callbacks from inactive host instances. Release subscriptions and cancel requests on unmount. Preserve drafts only under an explicit data-handling policy. Retained data needs visible freshness and must not imply live operation. Shell-wide identity failure requires a consistent session message rather than unrelated per-app errors.

K. Security considerations

Treat shell, application origins and backends as separate trust boundaries. Trust is granted through approved configuration, not through UI similarity. Validate launch targets and redirect destinations. Avoid shell tokens in URLs, logs or cross-window events.

For cross-origin messaging, send to a specific expected origin; validate sender origin, source window, message type, version and payload before acting. Never evaluate message content or allow arbitrary navigation/API calls. The MDN postMessage reference explains origin targeting and receiver validation. Messaging creates an intentional bridge across isolation and should remain minimal.

Frames require deliberate sandbox and browser feature permissions. Same-origin embedded content can have stronger access than an operator expects; separate origins may be needed for isolation. Web Components provide composition and style scoping, not a hostile-code security boundary. Same-realm micro-frontends are trusted code and require dependency governance.

Use HTTPS, backend input validation and authorization, appropriate content security policy, secure cookie policy, session expiry handling and minimal sensitive telemetry. The architecture does not establish safety classification or approve operational command semantics. Those require supplied stackup requirements.

M. Open questions and assumptions

  • What hosting origins, embedding policies, routes and supported browsers do the four applications provide?
  • Does BLOS permit frames, supply lifecycle messages or prefer launch-only integration?
  • What identity provider, role model, session policy and network boundaries apply?
  • Which API versions, contracts, health evidence and error taxonomies are available?
  • Which system-level alerts, if any, need aggregation and who owns acknowledgement?
  • What display resolution, physical viewing distance, luminance, ambient lighting and pointer hardware define the console?
  • Is simultaneous multi-application viewing needed, and how should navigation preserve unsaved domain work?
  • What security, audit, availability and operational assurance requirements apply?
  • Who owns registry approval, design-system governance, compatibility testing and rollback?

Assumptions are limited to browser access, independently developed interfaces and REST backends as supplied by the owner. Generic UI examples are not evidence of actual stackup capabilities. Final architecture and visual selection remain subject to these answers and operator evaluation.

SCOPE UI design requirements

Purpose and operator environment

Explore a common operator experience across independent BLOS, Display, Sensor Calibration and Native LOS boundaries. BLOS already exists and is not redesigned. All prototype content is abstract, local and simulated.

The intended console is used for extended sessions in a dark room with blue ambient lighting. Operators may be familiar with modern gaming interfaces. Borrow responsiveness, legible organization and immediate feedback; avoid decorative science-fiction treatments. Physical display, viewing distance and ambient luminance remain unknown.

Objectives: fast orientation, low cognitive workload, restrained luminance, stable navigation, recognizable abnormal states and consistent keyboard/mouse behavior. No final concept is selected by this exploration.

Interaction requirements

  • Thirteen top-level tabs: twelve full concept names and Comparison. Only one concept occupies the workspace. Arrow keys and Home/End activate adjacent tabs; Tab leaves the tab list.
  • Each concept has Workspace and Style Guide views. The same data and control state persist across concept changes for direct comparison; reload resets the session.
  • Application buttons change the placeholder context. Native LOS remains selectable to expose its unavailable explanation. No operational connection or retry is implied.
  • Review/Compare radios are exclusive. Locked is disabled and unselected. Style-guide specimens also show disabled-selected independently.
  • Checkbox controls an annotation in the disclosure. Switch updates the enabled/paused label. Preset selection updates feedback. Cards update the selected panel and feedback.
  • Label editing immediately changes draft context. Apply rejects blank/whitespace-only input and otherwise opens confirmation. Confirm increments a local saved revision; cancel preserves draft edits.
  • Increase value adds one. Reset confirms then restores form and value defaults, preserving concept/application selection and event history.
  • Sample error reports an intentional local failure; loading example disables repeat activation for 600ms before success.
  • Enabled specimen controls provide notification feedback. Native fields, disclosures and navigation produce observable state changes. Disabled controls cannot activate.
  • Notifications retain the latest message until another interaction; event history shows five recent logged workbench actions. No backend or persistent storage exists.

Primary actions use accent fill and dark ink, secondary actions raised fill and a solid border, tertiary actions transparent underlined text. Radios use a native selected dot; checkboxes a tick; switches thumb position and fill. Native glyph activation supplies pressed feedback. Fields use the background token and invalid/error messaging. Cards and navigation share hover/focus/pressed rules with buttons; active cards add selected text. Passive status indicators have no pressed/selected behavior. OS dropdown menus may differ by browser.

Each guide pins state appearances in labeled specimens while the actual controls demonstrate pointer and keyboard behavior. A pinned focus specimen does not mean it actually holds keyboard focus. Radio specimens use independent groups where necessary; the additional live group demonstrates exclusivity.

Per-concept style-guide requirements

Each guide describes philosophy, HEX palette, semantic colors, surface colors, font families/sizes/weights, spacing, grid, navigation, buttons, radios, checkbox/switch, fields/dropdowns, cards/panels, statuses, alerts, chart rules, control states, accessibility and dark-room rationale. CSS tokens and concept configuration drive both rendering and guide text.

Export Style Guide to PDF invokes browser printing of the active concept's dedicated guide. The print layout uses paper-friendly ink, lists original screen HEX values, preserves swatches when background graphics is enabled, includes component/state examples and excludes unrelated concepts and workspace. The operator chooses Save as PDF and a filename; the page does not silently download a PDF. Browser pagination and native form-glyph rendering may vary.

Accessibility and human factors

Use descriptive labels, headings, fieldsets/legends, native controls and explicit tab relationships. All workbench targets have at least 44px height through their labels; Industrial HMI actions are at least 48px and application buttons 56px. Focus must be distinguishable from hover and selection. Dialogs start on Cancel, contain focus through native modality, support Escape and restore focus. Tooltip information is available on hover, focus or click; Escape dismisses it.

Use text/symbol redundancy for statuses. Retain stable application order and avoid flashing, glow or autonomous content motion. All layouts stack below 760px, with a common intermediate layout below 1100px. The comparison matrix scrolls in a labeled keyboard-focusable region. Font zoom and narrow viewports require review; no full assistive-technology conformance claim is made.

Restrict bright areas in the screen interface. Text, controls and status differentiation need contrast review against the actual surfaces; reduced-opacity disabled controls remain identifiable as unavailable. Screen contrast measurements cannot establish dark-room comfort. Evaluate glare, blue ambient lighting, viewing distance, task timing, fatigue and status recognition with representative operators before final selection.

Prototype constraints

One HTML file with embedded CSS/JavaScript; no external assets, web fonts, packages, runtime requests or server requirement. No production framework or domain functionality. No telemetry or storage. src/ remains reserved. Synthetic event timestamps describe local action sequence, not wall-clock activity. Presets and modes change visible local state only; they do not claim to configure an application. The reference chart is intentionally static.

These are preliminary qualitative design assessments of the implemented mockups, not experimentally validated usability results. No concept is selected as a final design. Twelve design directions

1. Mission Control Console

A steady operational frame: permanent left navigation, a central workspace and a dedicated event rail.

  • Layout and navigation: Three-column 210px / flexible / 260px grid; summary above central controls. Square panel edges and 14px gutters. Persistent left application list; selected item has a leading inset bar.
  • Visual treatment: background #0D141E, panel #151F2C, accent #82B9D6; ui-monospace, Consolas, monospace; 3px base corner radius.
  • Advantage and limitation: High density and permanent rails suit broad consoles; narrow screens need stacking.
  • Human factors: Stable scan paths and subdued steel tones help recognition during long sessions. Monospaced labels can slow prose reading.

2. Modern Engineering Dashboard

An open dashboard with generous cards, rounded surfaces and horizontal application navigation.

  • Layout and navigation: Horizontal application bar, full-width summary, then flexible workspace and 290px event rail. 20px gutters. Top application strip keeps tools together without a permanent left rail.
  • Visual treatment: background #111B20, panel #19282D, accent #8FC9BC; system-ui, sans-serif; 14px base corner radius.
  • Advantage and limitation: Approachable and legible, with lower peak information density.
  • Human factors: Soft panel grouping reduces visual clutter; generous spacing reduces capacity on smaller consoles.

3. Gaming-Inspired Operator Console

Responsive, assertive interaction cues with angular navigation and a restrained lavender accent.

  • Layout and navigation: 190px left navigation, flexible central workspace, 240px event rail. Uppercase headings and accent edge markers. Angular uppercase application buttons with a strong selected leading edge.
  • Visual treatment: background #13131E, panel #1F1F30, accent #B7A2E3; system-ui, sans-serif; 4px base corner radius.
  • Advantage and limitation: Strong recognition at the cost of greater visual emphasis.
  • Human factors: Immediate selection cues borrow interaction clarity from games. Repeated accent edges may compete with warnings.

4. Minimal Dark Console

Content first, with a centered single-column workspace, quiet typography and separators instead of boxes.

  • Layout and navigation: Centered maximum 1100px single column; inline navigation, summary row, workspace, then event strip. 28px gaps. Inline application buttons above content; section order follows a simple reading path.
  • Visual treatment: background #14181C, panel #1B2228, accent #C0C8CE; system-ui, sans-serif; 4px base corner radius.
  • Advantage and limitation: Excellent calmness, but less simultaneous context and weaker partitioning.
  • Human factors: Few panel edges reduce competing visual cues. Long vertical scans can hide secondary context.

5. Modular Engineering Workspace

A tiled engineering workbench with visibly bounded modules and title bars.

  • Layout and navigation: Two equal columns: application tile / stacked summary, then controls / event module. 16px gutters; controls stack. A two-by-two application tile group identifies independent boundaries.
  • Visual treatment: background #101720, panel #1A2533, accent #A5BFE6; system-ui, sans-serif; 6px base corner radius.
  • Advantage and limitation: Good modular identity; fixed tile proportions may waste space. Tiles are not draggable.
  • Human factors: Explicit module edges support chunking. Equal columns give event history more space than some tasks need.

6. Tactical Flat Interface

Flat, compact blocks with firm alignment, square targets and subdued olive neutrals.

  • Layout and navigation: 180px left application rail, central summary and workspace, then a horizontal event row. 12px gutters. Compact left rail with uppercase section hierarchy and square controls.
  • Visual treatment: background #171C18, panel #222B24, accent #B9C59A; system-ui, sans-serif; 0px base corner radius.
  • Advantage and limitation: Efficient use of space, with a less relaxed visual rhythm.
  • Human factors: Low saturation and predictable edges help scanning. Compact grouping needs spacing review under fatigue.

7. Industrial HMI

Large targets, strong borders and an application bank on the right support deliberate actions.

  • Layout and navigation: Flexible controls on the left, 300px right application bank and event area. Two-pixel metric borders; 20px spacing. Right-side application bank uses 56px minimum buttons; other actions are at least 48px high.
  • Visual treatment: background #1C1A17, panel #2A2721, accent #E4BD7B; system-ui, sans-serif; 3px base corner radius.
  • Advantage and limitation: Highly explicit controls; warm action accent competes with semantic warning color.
  • Human factors: Large controls and clear labels reduce fine pointing demands. Amber primary actions need separation from warning badges.

8. Command Center Dashboard

An overview-led composition with top application navigation and a persistent event column on the left.

  • Layout and navigation: Top app bar; 230px event column left of summary and controls. First metric receives extra width and surface emphasis. Horizontal application strip beneath the concept heading.
  • Visual treatment: background #121824, panel #1D2739, accent #9BAFE5; system-ui, sans-serif; 6px base corner radius.
  • Advantage and limitation: Strong context retention; users must learn the event-first left column.
  • Human factors: Event context stays visible beside controls. The wide overview may draw attention away from the current task.

9. Precision Instrument Console

Measured alignment, numeric typography and small ruler-like marks establish an instrument-panel rhythm.

  • Layout and navigation: 220px left navigation with events underneath; summary and controls on the right. 18px gutters and fine rules. Persistent left list with event history immediately below.
  • Visual treatment: background #111A1D, panel #1A292E, accent #94CCD1; system-ui, sans-serif; 2px base corner radius.
  • Advantage and limitation: Excellent numeric scanning; fine structures need checks at distance.
  • Human factors: Tabular values support comparison. Decorative ruler marks are subordinate and carry no measurement meaning.

10. Contemporary Desktop Interface

A familiar desktop-like composition with a quiet sidebar, inset work surface and softly raised panels.

  • Layout and navigation: 200px left sidebar, central controls and 260px event rail. Work surface uses the raised token; rounded window-like panels. Sidebar selection uses a filled surface and leading marker.
  • Visual treatment: background #171821, panel #242633, accent #B7B2EA; system-ui, sans-serif; 12px base corner radius.
  • Advantage and limitation: Easy onboarding, though multiple surface layers add visual depth.
  • Human factors: Familiar patterns reduce initial learning. Nested surfaces must remain distinct at low luminance.

11. Adaptive Information Dashboard

A task-first workspace with summary and events in a secondary right column, plus progressive disclosure.

  • Layout and navigation: Top application bar; wide left controls, 320px right stacked summary and events. Single-column form and expandable context. Top application strip; responsive stacking adapts to viewport, never automatically reorders by live data.
  • Visual treatment: background #121C19, panel #1D2D26, accent #A5CCAE; system-ui, sans-serif; 9px base corner radius.
  • Advantage and limitation: Low task distraction; more scrolling within the longer main form.
  • Human factors: Prioritizes the current task and hides secondary prose. Summary context is less prominent than in overview-led concepts.

12. Hybrid Operator Console

Stable left navigation, an overview spanning the workspace and a quieter secondary event rail.

  • Layout and navigation: 195px application rail; summary spans center and 250px event rail. Controls stay central; secondary events use dashed framing. Persistent left list preserves application position across selections.
  • Visual treatment: background #11191F, panel #1A2832, accent #8FC9CF; system-ui, sans-serif; 7px base corner radius.
  • Advantage and limitation: Promising balance; its combined vocabulary needs operator evaluation.
  • Human factors: Balances overview and task focus with a restrained cyan accent. Three regions still require a broad display.

Promising candidates

Hybrid Operator Console balances a stable left rail, broad summary and central task area. It is a promising general console candidate if the target display supports three simultaneous regions.

Modern Engineering Dashboard favors legibility, familiar components and generous spacing. It merits evaluation when overview and approachability matter more than peak density.

Mission Control Console offers persistent context and predictable scan paths. It merits evaluation for broad engineering consoles, with particular attention to monospaced prose and sustained visual load.

These candidates match the Comparison tab. Industrial HMI remains useful when pointing precision and larger targets dominate; Minimal Dark Console is useful as a low-clutter reference. The other concepts test meaningful alternative navigation and hierarchy choices rather than serving as lower-ranked aesthetic variants.

Shared conventions and responsive behavior

Every concept implements native forms, separate focus and selection, confirmation, local notifications, semantic statuses and a guide with visual state references. At widths below 1100px they converge on a common two-column fallback; below 760px they stack. This intentionally prioritizes usable narrow-screen behavior over preserving every desktop distinction. All concept state survives switching, allowing direct comparison without different data.

Style guides list actual tokens and explain primary/secondary/tertiary actions, exclusive radios, checkbox/switch states, fields, cards, tabs, notifications and the static reference chart. Print layouts use paper-friendly ink while listing original screen HEX values; browser Save as PDF is user initiated.

Limitations and evidence needed

The matrix judges composition from design reasoning, not operator performance. There are no task completion times, error rates, fatigue measurements or population studies. Younger operators familiar with games are an anticipated audience, not evidence that decorative gaming treatments improve performance.

Evaluate the intended display and blue ambient environment with representative operators: compare navigation time, error recognition, keyboard-only use, focus visibility, long-session comfort, distance legibility and information density. Vary tasks and ordering to reduce familiarity effects. Assess zoom, screen reader behavior and print pagination separately. Token contrast checks alone do not establish accessibility or dark-room comfort.

The application content is a generic boundary demonstration. A final design may change once actual information categories, alert semantics, hosting constraints and existing application integration contracts are supplied. See Architecture, Design Requirements and Validation.
